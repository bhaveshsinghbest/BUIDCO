BUIDCO Project Monitoring Dashboard

Presentation notes — project overview, architecture, code flow and likely questions

1. What the project is

A web dashboard that lets BUIDCO (Bihar Urban Infrastructure Development Corporation) track every urban infrastructure project in one place — from sanction, through tendering and construction, to O&M handover.

It replaces scattered Excel sheets with a single live system that senior management, project directors and office staff all read from.

The problem it solves

  • Project data lived in many Excel files and emails — no single source of truth.
  • Management had no live view of progress, delays or money spent.
  • No record of who changed what, so data could not be trusted or audited.
  • Expiring bank guarantees and O&M contracts were easy to miss.

How the parts talk to each other

  • The frontend is a static build (HTML, CSS, JS). Vercel serves it from a CDN — there is no React code running on a server.
  • The browser calls /api/… on its own domain. Vercel rewrites those calls to the Render backend.
  • Because the call looks same-origin to the browser, there is no CORS preflight, cookies flow normally, and the backend URL is never exposed in the UI.
  • The backend is a REST API returning JSON. It never returns HTML.
  • Express talks to PostgreSQL through Drizzle ORM, a type-safe query builder.

Example: opening the Projects page

  1. User clicks Projects in the sidebar. React Router renders ProjectsPage.
  2. The page calls a hook — useListProjectsQuery(filters).
  3. RTK Query checks its cache. If the data is fresh it renders immediately and stops here.
  4. Otherwise it calls baseQuery, which attaches Authorization: Bearer <access token> from the Redux store.
  5. The browser sends GET /api/projects. Vercel rewrites it to the Render backend.
  6. Express runs its middleware chain: Helmet → CORS → JSON parser → cookie parser.
  7. requireAuth verifies the JWT signature and expiry, then attaches req.user.
  8. A permission gate runs (for example requireProjectCreate). MD bypasses all gates; other roles need the flag on their account.
  9. Zod parses the query string. Invalid input returns 400 before the database is touched.
  10. The service layer (projectsService) holds the business logic and builds the query.
  11. Drizzle ORM turns that into SQL. If the user is a PD, a division filter is added so they only see their own division.
  12. PostgreSQL returns rows; the service shapes them into clean JSON.
  13. The route responds { items, total }.
  14. RTK Query stores the result under a cache tag (ProjectList) and the component re-renders with data.
  15. Later, any create/update/delete invalidates that tag, so the list refetches automatically — no manual refresh code.

6. Login and session flow

  1. User submits username and password to POST /api/auth/login.
  2. The server finds the user and compares the password against the bcrypt hash.
  3. On success it issues two tokens: a short-lived access token (JWT, 15 min) returned in the JSON body, and a long-lived refresh token (30 days) set as an httpOnly cookie.
  4. The access token is kept in Redux memory — never in localStorage, so a script on the page cannot steal it.
  5. When the access token expires, an API call returns 401.
  6. baseQuery catches that, calls /api/auth/refresh once, gets a new access token, and retries the original request automatically. The user notices nothing.
  7. If the refresh itself is rejected, credentials are cleared and the user is sent to the login page.
Nice detail to mention: refresh tokens are rotated — each use issues a new one and retires the old. Reuse of a retired token is treated as theft. A short grace window stops two browser tabs refreshing at the same moment from logging each other out.

Standard error format

Every failure returns the same shape, so the UI can handle errors in one place:
{ "error": { "code": "VALIDATION_ERROR", "message": "…", "details": { … } } }

10. Two features worth explaining in depth

Excel import

  • User downloads a template whose columns are generated from the same field list the API uses.
  • The filled file is parsed in the browser with ExcelJS and every row is checked.
  • Errors are shown per row. If any row is invalid, nothing is imported — it is all-or-nothing.
  • Valid rows are posted to the API, which re-validates with the same Zod schema and inserts them in one transaction.

Audit trail

  • Services record an audit entry whenever a record is created, updated or deleted.
  • audit_log stores who, what and when; audit_log_change stores old and new values per field.
  • This makes the system defensible in a government review — every number can be traced back.

Security, Deployment & Likely Questions

The last page to revise before you present

11. Security

Password storageHashed with bcrypt. Plain passwords are never stored or logged.
AuthenticationShort-lived JWT access token in memory + rotating refresh token in an httpOnly cookie.
Token theft defenceRefresh tokens rotate on every use; reuse of an old token is detected and the chain is revoked.
Authorisation (RBAC)Four roles — MD, Admin, PD, Viewer — plus per-user flags for create / update / delete. MD bypasses all flags.
Data scopingA PD only sees their own division. Requests for other divisions return 404, so the existence of other data is not leaked.
Input validationZod validates every request at the API edge — bad data is rejected with 400 before reaching the database.
HTTP hardeningHelmet security headers and a CORS allowlist of permitted origins.
Rate limitingUpstash Redis limits login attempts and uploads to slow brute-force attacks.
AccountabilityFull audit log of every change, with field-level detail.

Important point to make: hiding a button in the UI is only cosmetic. Every rule is enforced again on the server, because the API is what actually protects the data.

12. Deployment

FrontendVercel — auto-deploys on every push to main. Live at buidco.vercel.app.
BackendRender — runs the compiled Express server. Reached through a Vercel rewrite of /api/*.
DatabasePostgreSQL — a managed cloud Postgres instance in production; a local Postgres server for development.
ConfigAll secrets come from environment variables — nothing sensitive is committed to git.
Known limitation, good to admit: the backend runs on Render's free tier, which sleeps after about 15 minutes idle. The first request then takes roughly 35 seconds. Fix: a scheduled ping to keep it warm, or a paid instance that never sleeps.

13. Questions you may be asked

Why route API calls through Vercel instead of calling Render directly? — It makes the call same-origin, so there is no CORS preflight, cookies work naturally, and the backend URL stays hidden.
Why two tokens instead of one? — The access token is short-lived, so a stolen one is useless quickly. The refresh token is httpOnly, so JavaScript cannot read it.
Where is role-based access actually enforced? — In backend middleware. The UI also hides controls, but that is only for convenience; the server is the real gate.
Why Drizzle ORM and not raw SQL or Prisma? — It is type-safe and lightweight, reads close to SQL, and its migrations are plain .sql files we can review.
How do you stop bad data getting in? — Zod validates at the API edge, and the Excel import reuses the very same schema, so bulk and manual entry obey identical rules.
How are the dashboard numbers calculated? — With SQL aggregates and database views, not in the browser. That keeps it fast and consistent for everyone.
What happens if two tabs refresh the session at once? — Token rotation has a short grace window, so parallel refreshes do not log the user out.
How is the project tested? — 101 Vitest unit tests, Playwright end-to-end tests, and an automated audit suite that captures before/after evidence.
How would you scale this? — Database indexes on foreign keys are already in place; next steps are connection pooling, cached KPI queries, and a paid always-on backend.
What was the hardest part? — Session handling. Users were being logged out when a request merely timed out, so we separated “server said no” from “server did not answer” and only ended the session for the first.
